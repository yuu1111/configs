# document-style-checkの設計

## 目的

文書、Markdown、コメントへ適用する文体基準をAIエージェントに守らせるため、機械的に判定できる部分をモデルの外側のCLIへ移す

指示文は読まれないことがあり、読まれても実行される保証がない 判断が要る部分は基準を読ませたうえで記録として残し、それ以外は決定的な検証にする

## 二層に分ける

- 機械検証層の `lint` は、意味を持たない違反を検出する errorはすべて整形で解消できる
- 判断記録層の `scan` と `check` は、文体の判断が必要な箇所を候補として書き出し、判断と根拠が記録されているかを確認する

判断そのものは自動化できない 記録できるのは、どの候補にどの判断をしたかという証跡だけになる このため `check` の成功は文体判断の正しさを意味しない

## 機械検証層

### 対象

- 拡張子が `.md` と `.markdown` のfileを対象にする
- 対象pathにはfileとディレクトリを指定でき、省略時はカレントディレクトリ以下を走査する
- 走査では `.` で始まるentryと `build`、`coverage`、`dist`、`node_modules`、`out`、`vendor` を除外する
- `--ignore` に渡したpathは、そのpath自身と配下を除外する

### rule

| rule | 検出内容 |
|------|---------|
| `consecutive-blank-lines` | 段落の区切りを超える連続空行 |
| `date-anchored-statement` | 確認日を対象の識別に使う記述 |
| `hard-break-html` | 本文中の `<br>` |
| `trailing-backslash` | 本文行の末尾のバックスラッシュ |
| `trailing-whitespace` | 行末の空白 |

`date-anchored-statement` だけがwarningで、残りはerrorになる errorは整形で解消できるが、確認日を対象の識別に使う記述は判断が必要なため整形しない

### 位置を保つ

- 検出は `file`、行、桁で示す
- インラインコードは同じ長さの空白へ置き換えてから検索するため、置き換え後の桁が元の本文とずれない

### 検査しない範囲

- frontmatterとコードフェンスの行
- インラインコードの中身
- 見出し、リスト、表などの構造行の末尾バックスラッシュ

### 整形

- 行末空白を本文行から除く
- インラインコードの外側にある `<br>` を除く
- 構造行を除いた本文行の末尾バックスラッシュを除く
- 連続する空行を1行へ畳む
- frontmatterとコードフェンスの行はそのまま残す
- BOMと改行codeは元の本文に合わせ、同じ入力には同じ結果を返す

## 判断記録層

### 候補の抽出

- `proseBoundaries` は空行で区切った本文ブロックの隣接関係を候補にし、両側とも構造行でない境界だけを残す
- `proseLineBreaks` は同じ段落内の単一改行を候補にし、段落内と箇条書きの継続行を `prose` と `list-continuation` で区別する
- `proseLongLines` は既定160文字以上の本文行を候補にし、箇条書きの項目を `list-item` として区別する
- 候補はすべてidを持つ 本文を編集するとidの対応も変わるため、記録は特定の本文に対してだけ有効になる

### 判断基準の抽出

- 基準fileはMarkdownで、`## 判断基準` の節にある `###` 見出しを基準として読む
- コードフェンス内の見出しは無視する 同じ基準の重複と、判断基準の節の重複は拒否する
- 基準をパッケージへ同梱しない document-style skillの `SKILL.md` が基準fileの一例になる

### 記録の形式

```json
{
  "version": 1,
  "rules": "/path/to/SKILL.md",
  "rulesSha256": "...",
  "criteria": [{ "criterion": "...", "decision": "", "evidence": "" }],
  "documents": [
    {
      "document": "/path/to/doc.md",
      "documentSha256": "...",
      "boundaries": [
        { "id": "L1-L3", "before": "...", "after": "...", "decision": "", "reason": "" }
      ],
      "lineBreaks": [],
      "longLines": []
    }
  ]
}
```

- `criteria` は `checked` または `not_applicable` と根拠を埋める
- `boundaries`、`lineBreaks`、`longLines` は `keep` と理由を埋める
- `documentSha256` と `rulesSha256` はbyte列のhashで、本文か基準を編集すると記録は無効になる

### checkが確認すること

- `version`、`rules`、`rulesSha256` が現在の値と一致する
- 文書の並びが記録時と同じで、各 `documentSha256` が一致する
- 各groupのidが欠落、追加、並べ替えなく揃っている
- 候補の文脈が記録時のままである 判断欄と理由欄以外の変更を改変として検出する
- すべての項目に判断と根拠がある

`check` は文体判断の正しさを判定しない 記録の網羅性と、記録後の本文変更の有無だけを確認する

## CLIの契約

| サブコマンド | 動作 |
|--------------|------|
| `scan` | 候補と基準を抽出し、未確認の記録を書き出す |
| `check` | 埋めた記録を現在の本文と基準に対して確認する |
| `lint` | 機械的な違反を報告し、`--write` で整形する |

| option | 動作 |
|--------|------|
| `--rules <path>` | 判断基準を持つ基準file `scan` と `check` では必須 |
| `--review <path>` | 読み書きする検証記録file |
| `--ignore <path>` | 検査から外すpath 複数指定できる |
| `--write` | 報告の代わりに整形を適用する |
| `--json` | 検出をJSONで出力する |

- `scan` は既存のfileを上書きしない 古い記録を無条件に信じないため、常に新しい名前へ書き出す
- 終了codeは0が成功、1が違反または確認の失敗、2が引数または設定の失敗

## 品質ゲートへの組み込み

- `quality-check` のengineとして `lint --json` を起動する 検出は `errors` と `warnings` の配列で返し、1件ずつ対象file、行、桁、rule名、表示用の文を持つ
- engineはbaseline差分の対象になる 既存の違反が残るrepoでも、新規の違反だけを失敗として扱える
- 判断記録は自動検出ではないためゲートに含めない ゲートは機械検証だけを実行し、記録の作成と確認は文書を編集する側の手順として残す

## 境界

- 文体判断そのものを自動判定しない 記録の網羅性だけを検証する
- 会話、コード本体の整形、責務分離、ディレクトリ構成は対象外とする
- 基準を同梱しない 対象repoの基準fileを `--rules` で渡す

## 拡張するとき

- ruleを足すときは `RuleId`、`RULE_IDS`、`MESSAGES` と検出を更新し、整形できるかを決める
- 候補の種別を足すときは抽出関数、記録のgroup、`verify` の確認項目を揃えて更新する
- 基準fileの形を変えるときは `criterionNames` と記録スキーマの両方を確認する
